Special Methods & the Data Model

Every time you write len(x), a + b, a == b or print(x), Python turns the syntax into a call to a method with a reserved name, such as __len__ or __add__, and looks that method up on the object's class. Define those methods and your own classes work with the language's syntax. Get __eq__ and __hash__ out of step and you get a class that can't go in a set, or a set that can't find what's in it.

~40 minutes
5 interactive demos
Builds on Sessions 03, 04 and 06
Learning goal

Syntax is a method call, looked up on the class.

Python's data model is the list of specially named methods it calls for you. len(x) runs type(x).__len__(x), and v * 3 runs type(v).__mul__(v, 3). The search starts at the class, never at the instance, and ends at object, which has a fallback for a few of them. Everything else in this session follows from that.

type(x) __repr__ __mul__ NotImplemented __hash__

3 Then equality and hashing. Demos 4 and 5 are the pair behind most real bugs here: a class that suddenly can't go in a set, and a set that loses an object it still holds.

Syntax is a method call on the type

In plain words A universal remote has the same buttons whatever it's pointed at: power, volume, channel. What a button does depends on the device. Python's syntax is the buttons. Each class decides what they do by defining methods with reserved names, and Python presses the one that matches what you wrote.

These methods have two underscores on each side, so people call them dunder methods. len(x) becomes type(x).__len__(x), a * b becomes type(a).__mul__(a, b), and a == b becomes type(a).__eq__(a, b). The search starts at type(x), follows the MRO from Session 04, and never reads the instance's __dict__. If no class on the way defines the method, either object has a fallback (it does for __repr__, __str__, __eq__ and __hash__) or you get a TypeError.

Key
Why the class, and not the instance
The Python docs give the sharpest reason. A class is an object too, so repr(Point) has to describe the class. If the search started in Point's own namespace, it would find the __repr__ written for points and call it with no point to work on. Looking on the type keeps the two apart: the type of p is Point, and the type of Point is type. It's faster as well. CPython keeps a table of these methods for every class, filled in when the class is created and refreshed when you assign one to the class, so len(x) reads one entry instead of searching dictionaries.
Try this in a REPL

(3).__add__(1.5) returns NotImplemented, because int doesn't add floats. 3 + 1.5 still gives 4.5: after the int declined, Python called float.__radd__(1.5, 3). Then try len("abc") == type("abc").__len__("abc"), which is True.

Showing an object

__repr__ for developers, __str__ for users

In plain words A repr is a name badge for developers: it says what the object is, ideally in a form you could type back in. A str is the friendly version you'd show a user. If you only write one, write the badge, because Python falls back to it when there's no friendly version.

repr() is what the REPL shows, what debuggers and !r in an f-string use, and what every container uses for its items. str() is what print, f-strings and format() use. object.__str__ calls repr, so a class with only __repr__ looks right everywhere. A class with only __str__ prints nicely on its own and turns back into <__main__.Point object at 0x...> inside a list.

python
class Point: def __init__(self, x, y): self.x = x self.y = y def __repr__(self): return f"Point({self.x!r}, {self.y!r})" def __str__(self): return f"({self.x}, {self.y})" p = Point(3, 4) print(p) # (3, 4) print([p]) # [Point(3, 4)] print(f"{p!r}") # Point(3, 4)
Care
Use !r inside a repr
f"User({self.name!r})" gives User('Ada'), with quotes, so a string is visibly a string. Without !r you'd get User(Ada), which looks like a variable. Keep a repr cheap and free of side effects too. It runs in debuggers, logs and error messages, often after something has already gone wrong.
Operators

Operators: the left side is asked first

In plain words Two people reach the till together and one of them has to pay. The person on the left is asked first. If they say they can't, the person on the right is asked. If both say no, nobody pays, and there's a scene.

a * b calls type(a).__mul__(a, b). If that method is missing or returns NotImplemented, and b is of a different type, Python calls the reflected method type(b).__rmul__(b, a). If that's missing or returns NotImplemented too, it raises TypeError: unsupported operand type(s). There's one exception to left first: when b's type is a subclass of a's type and overrides the reflected method, b is asked first, so a subclass can take over from its parent.

1 · Left

The left operand's class

type(a).__mul__(a, b) gets the first chance. Any result other than NotImplemented is the answer, and nothing else runs.

2 · Right

The reflected method

Only when the types differ: type(b).__rmul__(b, a). The operands are swapped, so self is always an instance of the class the method belongs to.

3 · Neither

TypeError

Both declined, so Python raises unsupported operand type(s) for *, naming both types. That message is only right if your methods returned NotImplemented instead of raising.

Care
NotImplemented isn't NotImplementedError
Return NotImplemented, a value, from an operator method to say "not with this type". NotImplementedError is an exception, for a method that a subclass is meant to fill in. Raising it from __mul__ would stop Python before it asks the other operand. And don't test NotImplemented with if: using it as true or false is deprecated.
In place

a += b tries __iadd__ first

A list's __iadd__ extends the list itself and returns it, so every name sharing the list sees the change (Session 03). Without __iadd__, Python falls back to a = a + b, builds a new object and rebinds the name. Tuples, ints and strings work that way.

Comparisons

< reflects to >

If a.__lt__(b) declines, Python tries b.__gt__(a). == reflects to itself, and when both sides decline it falls back to identity instead of raising, which is why p == 5 is False in demo 4.

Try this in a REPL

[1, 2] * 2 and 2 * [1, 2] both give [1, 2, 1, 2]. (2).__mul__([1, 2]) returns NotImplemented, so the second one only works because the list was asked next.

Equality and hashing

__eq__ and __hash__ come as a pair

In plain words A cloakroom gives you a ticket number worked out from what your coat looks like. Sew a patch on the coat, then ask for it back, and the attendant works out a new number, looks on that hook and finds nothing. Your coat is still in the room, on the hook for the old number.

A dict or set finds an object in two moves: hash(key) picks a place, then == confirms the match. That only works if equal objects have equal hashes, and if an object's hash doesn't change while it's stored. By default both hold, because object.__eq__ and object.__hash__ both go by identity. Define __eq__ and you've changed what equal means, so Python sets __hash__ to None in your class, unless the class body defines __hash__ too.

1

Values that never change: define both. Hash a tuple of the same fields __eq__ compares. Money amounts, coordinates and dates are like this. A frozen dataclass does it for you.

2

Values that change: define __eq__ only. Leave the class unhashable, and when you need a dict, key it by something that stays put, such as an id.

3

Things with an identity: define neither. A connection, a game player or an open file is equal only to itself, and the default identity hash is right for it.

Read
is and == ask different questions
a is b compares addresses and never calls a method. a == b calls __eq__, which can return whatever its author chose. That's why the idiom is x is None: a class can make x == None return True, but nothing can make is lie.
Try this in a REPL

Define a class with an __eq__ and nothing else, then look at MyClass.__hash__: it's None. Take the __eq__ out, and MyClass.__hash__ is object.__hash__ is True again.

Dataclasses

@dataclass writes the methods for you

In plain words Most small classes need the same three methods: an __init__ that stores the fields, a __repr__ that shows them, and an __eq__ that compares them. A dataclass reads your list of fields and writes those methods for you.

@dataclass is a decorator in Session 06's sense, so it means Point = dataclass(Point). It reads the annotated fields from the class body, generates the methods, sets them on the class it was given, and returns that same class. With the default eq=True and without frozen=True, it sets __hash__ to None, by the same rule as demo 4.

python
from dataclasses import dataclass @dataclass(frozen=True) class Point: x: int y: int p = Point(1, 2) print(p) # Point(x=1, y=2) print(p == Point(1, 2)) # True print({p}) # {Point(x=1, y=2)} p.x = 10 # FrozenInstanceError: cannot assign to field 'x'
You write What lands in the class
@dataclass __init__, __repr__, __eq__, and __hash__ = None
@dataclass(frozen=True) The same, except that __hash__ is built from the fields, plus a __setattr__ and __delattr__ that raise FrozenInstanceError
@dataclass(order=True) __lt__, __le__, __gt__ and __ge__, comparing the fields in order, like tuples
@dataclass(slots=True) __slots__ for the fields. This option builds and returns a new class
Edge
Frozen is a strong hint, not a lock
object.__setattr__(p, "x", 10) still gets through, because it skips the class's own __setattr__. That's how the generated __init__ stores the fields of a frozen class in the first place. Nobody does it by accident, and accidents are what frozen protects against.
What you should be able to draw

A class namespace with special methods in it, and a lookup that starts at type(x) and walks to object without looking inside the instance. Two operands: the left one asked first, a NotImplemented, then the right one's reflected method. A class whose __eq__ arrived with __hash__ = None. And a set entry filed under a hash its object no longer has. Draw those four and you can predict every case in this session.

Common mistakes

Six ways this goes wrong

Defining __eq__, then using the objects as keys

The class became unhashable the moment it got an __eq__, so the first dict or set raises TypeError: unhashable type. Add a __hash__ from the same fields if the objects never change, or use a frozen dataclass.

Hashing fields that change

Nothing fails when you change the object. Lookups just stop finding it, as in demo 5, and the bug shows up far from the line that caused it. Hash only what's fixed for the object's whole life.

Raising instead of returning NotImplemented

An operator method that raises, or that crashes reading other.x from an int, never lets the other operand try. Check the type and return NotImplemented, and Python produces the right TypeError by itself.

Writing only __str__

print(obj) looks fine, while the REPL, the debugger and every list show <__main__.Point object at 0x...>. Write __repr__ first, since str() falls back to it.

Putting a special method on an instance

obj.__len__ = ... or obj.__call__ = ... changes nothing that len(obj) or obj() can see, because syntax looks on the class. Define the method on the class, and have it read data from the instance if the behaviour has to vary.

Forgetting that empty means false

A class with __len__ is false when its length is 0, so if playlist: skips an empty playlist that does exist. When you mean "is there one at all", write if playlist is not None:.

Check
Two questions catch nearly all of it
Which special method does this syntax call, and on which class will Python find it? The instance is never part of the answer. If I define ==, can my objects still be hashed, and can their hash change? Equal objects need equal hashes, and those hashes have to hold still.
Check your understanding

Can you predict the memory?

Every question comes back to which class answers, and whether a hash can change.

1. Playlist defines __len__, and you run mix.__len__ = lambda: 99 on one instance. What does len(mix) return?
Special methods are found on the class. The lambda sits in the instance's __dict__, where only an explicit mix.__len__() would find it. To change what len() does, change the class.
2. A class defines __repr__, returning "P", and no __str__. What does print(p) show?
print calls str(p), which finds object.__str__ on the way up from the class. That method calls repr(p), which finds your __repr__. One method covers both.
3. Vec defines __mul__, and __rmul__ = __mul__. In what order does Python try methods for 3 * v?
The left operand is asked first. The int can't multiply by a Vec, so it returns NotImplemented, and Python asks the right operand through its reflected method. Nothing is converted.
4. Your __add__ is handed a type it can't add. What should it do?
NotImplemented is a value that means "not with this type". Raising stops the search before the other side gets a turn, and returning None makes a + b evaluate to None, which is worse than an error.
5. Point defines __eq__ and no __hash__. What does {Point(1, 2)} do?
Hashing by identity would give equal points different hashes, which breaks dicts and sets. So Python switches hashing off for the class until you write a __hash__ that agrees with your __eq__.
6. p is in the set seen, hashed from (x, y). Then p.x = 10 runs. What is p in seen?
The set stored the hash when p went in and never works it out again. The lookup hashes p as it is now, finds no entry with that hash and stops. p is still inside, and only looping over the set would find it.
7. You write @dataclass above class P: with one field, x: int. What does {P(1)} do?
A dataclass follows the same rule as a class you write by hand. Pass frozen=True to get a __hash__ built from the fields, along with fields that can't be reassigned.
